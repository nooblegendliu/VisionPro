# 架构设计

## 1. 设计目标

方案级编排由 `WorkflowSession` 受理。`SolutionGraph` 声明流程间控制和公开端口映射，协调器按每个子句柄的实际完成推进后继。引擎复用已有准入、状态和结果生命周期。CLI 与桌面共用同一会话接口。[方案运行契约](data-model.md) · [协调器](../source/workflow/solution_run.cpp)

- 基础模型独立于界面和编辑器库。
- 工具接入不要求调度器理解具体算法。
- 配置、运行、显示和存储职责清晰。
- 支持逐步扩展，不提前建设完整工业平台。
- 同一方案可在不启动 GUI 时加载和执行，支撑测试、自动化和后续现场集成。

本文落实 C01–C10 设计基线；当前已实现 S2.1–S2.4 的核心领域类型、方案/关系模型、
配置快照、类型化请求、结果记录与复制重映射；S2.5 图/绑定静态校验已完成并通过 Release 验证。
S2.6 会话内结果访问和绑定解析已通过 Release 验证，S3 接通调度、准入、提交、取消与文件存储。
核心对象与契约以 [data-model.md](data-model.md) 为准；
手册依据、设计理由及阶段验收以 [requirements.md](requirements.md) 为准。
架构不得把早期调度、算法或存储后端的能力限制写成永久模型约束。

S5.1 已接通 Qt Widgets 和 QtNodes 通用图层。S5.2 已实现同会话配置发布，见 §5.3。
S5.3 已接通画布与属性编辑、文档及资源操作，见 §4.1 和 §9.1。S5.4 接通图像和 ROI。S5.5 接通桌面运行、调试和结果观察，见 §4.1 和 §8.1。
实施与验收见 [development.md §9](development.md#9-第五阶段实施与验收计划)。

## 2. 模块职责

| 模块 | 职责 |
|---|---|
| core | 标识、数据类型、图像与几何、工具描述、静态注册表和调用契约 |
| workflow | 方案和流程模型、绑定解析、校验、执行计划及运行数据服务 |
| tools | 内置算法、逻辑及显式数据收发工具的实现和注册 |
| infrastructure | 方案读写、资源解析、日志和外部适配 |
| ui | 流程编辑、参数配置、图像与结果显示 |
| app | 模块装配、应用命令和生命周期管理 |

初期不要求每个模块独立发布为动态库。

固定工件检测由方案连接平移定位、五个 ROI 颜色测量、闭区间判断、逻辑与和单次发送。每一路从同一次定位调用绑定像素变换，执行器沿普通控制边调度。类别图的只读标签和经校验的类别表由 core 定义，tools 提供灰度分段规则，ui 依据节点布局的配色绘制结果。[工件检测方案](../samples/s6-inspection/solution.json) · [数据契约](data-model.md#76-工件定位颜色测量与类别图)

逻辑分层与现有模块对应如下，不另建一套平行目录：

| 层次 | 模块 | 主要责任 |
|---|---|---|
| 应用层 | app、ui | 应用装配、无 GUI 入口与桌面交互 |
| 核心层 | core、workflow | 类型契约、模型、绑定、结果和执行控制 |
| 能力层 | tools、infrastructure | 具体算法、方案存储、设备及通信适配 |

分层表达职责，不表示核心层直接依赖所有能力实现。

### 2.1 S2 在整体架构中的位置

S2 实现 core 的基础类型与契约，以及 workflow 中的配置模型、校验和绑定解析。
这些内容既包括方案、节点、图像等领域对象，也包括复制重映射、结构检查和按运行取值的实际逻辑。
后续执行器、算法工具和界面共同使用这些接口，不另建各自的身份与数据模型。

S2.1 已建立 `visionpro_core` 静态库和独立测试程序，公共接口位于 `include/visionpro/core`，
实现位于 `source/core`。身份值、诊断及 `Result<T>` 使用标准 C++20；UUID 随机生成在实现文件中
调用 Windows CNG，系统头文件和链接依赖不进入公共头文件。当前只提供 Windows 后端，
非 Windows 配置明确报告不支持，后续平台适配不改变领域身份契约。
S2.1 当时尚无 `workflow` 目标；S2.4 新增该库，S2.6 接入结果访问和绑定解析器，运行服务仍按后续阶段推进。

S2.2 在同一核心库内加入 Schema/运行身份、不可变 `DataType` 和独立的 `ConfigValue`/`DataValue`，
以及参数、输入输出、控制出口和工具描述的校验。值按自身 Schema 检查字段、集合和枚举；
元数据检查必填性、默认值、约束、允许来源/转换和版本能力完整性，
不查询结果存储、不触发来源，也不执行转换、聚合或资源操作。
这些局部校验已由 S2.5 的图/绑定 Validator 和 S2.6 的 Resolver 复用；局部通过不能代替完整验收。

S2.3 继续使用标准 C++ 核心库，图像复制进入只读共享存储，裁剪视图持有父缓冲及到根图的坐标平移。
几何、ROI、配置掩膜和资源引用可进入配置值，实际图像/掩膜像素只进入运行值；发布值时复制可变容器，
不接管调用者仍可能通过元素指针修改的存储。坐标/变换、区域/掩膜能力、资源目录和状态记录具备独立校验入口。
资源、全局变量、队列、节点状态的定义与运行值分离，工具声明资源槽、状态 Schema 和图像/区域能力。
这些定义暂随 core 提供，以便工具契约和后续 workflow 共用；实际文件/设备解析、共享服务和状态调度仍归原模块。
没有资源读写、队列消费、状态 Init、真实区域栅格化或算法执行，也不增加 Qt/OpenCV 依赖。

S2.4 新增 `visionpro_workflow`（别名 `visionpro::workflow`），公开依赖 core，保持核心与界面独立。
该库持有可编辑 Solution/Workflow/Node、独立的控制/数据/包含关系、Group 公开输入及数据/控制导出，
并提供局部结构检查、层级枚举、子图/整方案复制与引用重映射。
ConfigSnapshot 固定配置和工具元数据副本；RunRequest 固定目标及独立的类型化输入；NodeResult 独立持有终态记录。
三者均不借用可变编辑容器。固定配置资源声明不等于已加载并锁定资源内容，准备请求也不等于已受理运行。
局部合法的编辑草稿可捕获快照；S2.5 增加完整引用/类型/依赖图静态校验，S2.6 提供 ResultStore，执行准入仍由后续模块完成。

S2.5 在 `visionpro_workflow` 内提供 `validate_solution`，复用 core 的元数据、值、资源和几何局部校验。
校验器接收 const 方案与工具目录，也可使用 ConfigSnapshot 的只读方案/工具；不会改写控制图或编辑顺序。
按 Workflow/Group 的显式入口计算控制可达范围，检查同层控制边、公开输入/数据及控制导出，
从普通输出绑定和嵌套 ROI 继承引用派生数据依赖，拒绝逆序、控制环、数据环和联合等待环。
通过时返回独立的 `ValidationIndex`：仅保存身份、作用域、可达节点、控制线和带绑定定位的数据依赖，
不借用可变节点，也不是执行计划或运行可用性的证明。未连接草稿仍检查引用与类型，但不会隐式成为入口。
非空 `SchemaSupport` 才启用声明的后端版本/能力检查；未提供时只验证元数据，不推断真实后端支持。
本层不启动节点、读取结果、加载文件、消费队列或访问设备；运行值解析归 S2.6，调度与准入归 S3。

S2.6 在同一 `visionpro_workflow` 库加入 `ResultStore` 和 `BindingResolver`，不增加模块依赖。
ResultStore 按会话、运行和逻辑调用保存人工终态记录，检查完整输出、真实值类型及领域引用，
拒绝重复调用和已退役运行；它是单线程结果访问结构，不承担 S3 的提交资格、取消竞争或重试裁决。
Resolver 持有通过静态校验的快照，从显式 `ResolutionContext` 取得作用域公开输入、来源调用选择和全局只读快照，
返回 Resolved/Pending/Unavailable/Failure 及来源记录，不按节点查最新值、不阻塞或触发生产者。
同静态宿主的祖先运行作用域只有在明确声明可见时才能读取，不能穿透 Group 公开边界。

资源解析在此阶段只校验目录并返回带实际版本声明的类型化引用，不打开文件或建立设备连接。
嵌套 ROI 保留原符号表达式与完整、独立持有的来源 Region（含排除项和修正），算法层以后完成几何求值。
全局值来自调用方显式提供的只读快照，不从定义初值补齐，也不宣称执行了跨变量原子读取。
当前没有共享写入、队列消费、状态调度、设备调度或真实算法；接口和验证范围见 data-model §5.7、§8.2.2。

S2.7 的工具调用契约位于 core：`ToolExecutionConfiguration` 保存工具所需的不可变配置投影，
`InvocationContext` 固定本次值和来源身份，`ToolInstanceFactory` 创建实例，`InvocationOperation`
区分完成通知、协作取消与实际退出。它们不包含 Solution、Node、ResultStore 或 GUI 类型。
类型化资源租约只负责访问权的拥有边界，实际连接、状态服务和实例装配仍由 S3 的服务/适配层负责。
工具结果是尚未提交的完成载荷，不能自行推进控制图或写入 workflow 的结果仓库。

workflow 的 `PreparedTool` 持完整 ConfigSnapshot 与 BindingResolver，将已解析值、ROI 来源和资源槽
投影到 core 调用契约；Pending、不可用或失败不能创建固定调用，更不会自动启动工具。
工具完成载荷回到 workflow 后校验身份与输出，形成 NodeResult；是否接受并推进后继仍须引擎仲裁。
`RunHandle`/`RunControl` 定义已受理运行的查询、等待和取消边界，`RunSubmitter` 留给 S3 实现原子准入。
S2 使用可控替身验证这些对象的保活和错误返回。静态工具装配见 §2.2，生产准入见 §2.3。
组合验收与逐项交接见 [development.md §8.10](development.md#810-s27-与-s2-整体验收记录)。

以下按参考软件中可观察的功能说明本项目的分工；依据见 [requirements.md](requirements.md) §2，
不据此推断 VisionMaster 内部使用相同类名或实现架构。

| 功能 | S2 提供的基础 | 后续接入 |
|---|---|---|
| 方案、流程、模块参数及 Group 公开边界 | Solution/Workflow/Node、工具元数据、公开 Schema、包含关系及配置快照 | S3 运行与保存加载；S5 编辑界面；S6 完整 Group 执行与复用 |
| 控制连线、分支和汇合 | 控制图、出口定义及控制/数据依赖联合校验 | S3 调度器决定何时调用、等待或关闭路径，并处理失败和取消 |
| 图像源和参数结果订阅 | Binding、结构化引用、Validator/Resolver，按本轮上下文定位和检查已有数据 | S3 在节点调用前解析输入，并根据就绪状态安排执行 |
| 图像、ROI 与位置修正 | 只读所有权、视图持有、区域和坐标模型及校验 | S4 算法适配；S6 完整形状、标定和设备缓冲适配 |
| 模块输出、状态和结果查询 | NodeResult、输出有效性、运行身份及最小结果访问结构 | S3 结果提交、生命周期及完成事件；S5 显示与观察订阅 |
| 全局变量、队列和外部设备 | 定义、消息类型、关联身份及资源引用，必要时用测试替身验证取值 | S6 共享读写、排队消费、业务汇合和设备通信服务 |

BindingResolver 负责数据定位和取值，不负责节点调度。
S2 用人工结果判断值、未就绪和错误；由 S3 调度器决定等待或结束，解析器不阻塞等待生产者或补跑来源。
同流程只读图像共享属于所有权和访问契约，不等于跨流程消息传输或外部通信已经实现。

S2 的结果访问结构以方案会话为边界，按 InvocationKey 寻址；跨会话记录补充会话身份。
人工结果的重复键处理不能静默覆盖已有结果，但其单线程验证不代表 C08 的原子终态提交、
取消竞争或迟到回调已经验证。运行句柄与工厂在 S2 形成可编译接口，S3 再实现运行服务与装配。
实施顺序及验证方式见 [development.md §5](development.md#5-第二阶段实施与验证)。

### 2.2 S3.1 工具装配与计划

`core::ToolRegistry` 按 `ToolTypeId` 保存工具描述、后端 `SchemaSupport` 和工厂。工具和应用装配方提供注册项，
`workflow` 只依赖注册接口。快照捕获可复用目录描述，规划逐个核对所选工具的配置版本、Schema 和所需能力。
显式创建实例时复用 `create_tool_instance` 的身份、所有权及异常检查。

`workflow::ExecutionPlan` 只读持有请求、验证索引、入口和固定工具配置。计划创建不调用工厂。
`PreparedTool` 使用计划的同一范围和请求解析绑定。同步与可控异步夹具验证工厂装配和调用边界。
接口及约束见 [data-model.md §5.8](data-model.md#58-s31-执行范围与计划)。

### 2.3 S3.2 内存执行

`workflow::WorkflowEngine` 实现 RunSubmitter，消费 S3.1 的线性同步计划。
S3.2 的准入锁保护 WorkflowRunId 分配、每流程占用槽和待执行工作队列。
每轮的 RunControl 独立持有固定请求、结果仓库与节点追溯。

工具创建和调用在锁外进行。每轮的运行控制锁协调取消、结果提交和进度查询。
计划释放后归还流程槽位，再发布 Quiescence。运行服务可由无 GUI 程序直接使用。
具体入口、同步取消和句柄寿命见 [data-model.md §4.6](data-model.md#46-s32-内存执行闭环)。

### 2.4 S3.3 异步执行与退出

异步操作的逻辑完成和实际退出分别唤醒同一工作线程。每轮只保留一个就绪标记，
唤醒按完整调用身份核对，完成和退出以操作对象中已保存的状态为准。
同流程的结果提交、取消和后继许可通过运行控制锁裁决。工具的协作取消入口在锁外调用。
操作实际退出并清理后，执行器交付其控制许可。整轮所有在途操作清理后归还槽位。
资源由调用方注入的租约提供方获取，执行器负责每次调用的持有期。详见 [data-model.md §4.7](data-model.md#47-s33-异步执行取消与实际退出)。

### 2.5 S3.4 分路调度

`workflow` 的运行控制按计划维护逐边到达和关闭、就绪节点及当前调用的结果提交资格。
控制边全部确定且有有效到达时，AllActivated 授予一次节点执行资格。绑定等待按派生数据依赖唤醒，
就绪队列由同一工作线程推进。每条在途异步调用保留独立的完成和退出状态。
FailFast 关闭待定控制边并排空已启动的调用。运行进度暴露节点和控制边状态，详见 [data-model.md §4.8](data-model.md#48-s34-分叉汇合与基本分支)。

### 2.6 S3.5 状态服务与单节点调用

`workflow` 在引擎内持有节点状态仓库，根据固定工具配置选择代次。工具通过 `core::ToolStateAccess` 读取和写入本次调用的类型化状态。
工具 Init 在锁外运行。每次调用的访问权保留至后端清理，流程槽内的运行与显式重置互斥。
声明在结果接受时写入的状态随成功结果在同一运行控制锁内提交。

单节点计划沿用调度和结果提交入口，以一个目标节点和零条外部控制边执行。
独立请求直接为目标固定输入，使用独立 RunIdentity，默认获得临时状态代次。
同流程的工作流请求、独立请求和活动状态重置通过同一准入锁协调。见 [data-model.md §4.9](data-model.md#49-s35-状态服务与单节点调用)。

### 2.7 S3.6 结果交付、观察与会话生命周期

`WorkflowEngine` 在每轮结果仓库之外维护有界会话索引，按实际清理顺序保留近期运行。
查询返回拥有只读数据的 `NodeResult`。索引释放后，调用方持有的 RunHandle、结果和图像仍可使用。
结果接受、逻辑终态和实际清理分别产生可选观察事件，订阅者从各自的固定容量队列读取。
必要完成与退出仍由 `InvocationOperation` 的状态和调度唤醒处理。

`WorkflowSession` 验证候选内存方案与工具能力，成功后关闭旧引擎的受理和观察交付，排空运行后发布新会话。
管理操作独立于运行身份。旧会话的调用及观察队列按原会话身份收尾。详见 [data-model.md §4.10](data-model.md#410-s36-结果交付与会话生命周期)。

### 2.8 S3.7 文件方案与诊断加载

`infrastructure` 将版本化 UTF-8 清单解码为拥有配置的 `SolutionDocument`，复用 workflow 的领域诊断。
JSON 类型只出现在存储模块内部。稳定 ID、三类关系和可持久化值进入清单，工具目录仍由调用方装配。

`FileResourceProvider` 解析显式基准，校验并持有固定文件字节，通过已有资源接口提供只读租约。
引擎对已选范围调用资源预检，再按原子准入规则受理。应用也可将完整候选交给 `WorkflowSession` 严格激活。
已知草稿、未知字段和解码失败的处理见 [data-model.md §10.2.1](data-model.md#1021-s37-清单与加载接口)。

### 2.9 S3.8 保存事务与故障保护

`infrastructure` 在 Windows 本地 NTFS 包目录内持锁核对清单、写入独立的托管文件版本，再同卷替换清单。
`SolutionDocument` 持有加载基线。S4.6 保存时逐字节比较原始清单，编辑模型和资源字节由调用方提交。只读加载在获取固定资源字节后复核清单，避免返回混合修订。

清单替换成功后才清理退役版本。托管文件的活动租约阻止文件删除，释放后可重试清理。提交结果与清理报告通过同一返回值交付。
接口和并发边界见 [data-model.md §10.4.1](data-model.md#1041-s38-保存与清理接口)。

### 2.10 S3.9 无 GUI 命令行装配

`visionpro_cli` 由 app 装配 `tools` 的静态模拟注册表、`infrastructure` 的磁盘方案与文件租约，以及 `workflow` 的运行服务。
模拟文件工具通过只读 `FileResourceLease` 取得固定文件内容。加法、命名分支、汇合与模拟交付沿用普通工具注册、绑定和控制契约。

`run` 等待已受理运行实际退出，再按本轮调用键查询结果。摘要使用引擎实际记录的派发顺序、绑定来源、资源租约引用及控制边状态。
`save` 通过同一加载入口取得基线并调用保存事务。命令和验收夹具见 [development.md §3.16](development.md#316-s39-构建与命令行验证)。

### 2.11 S4.1 可选视觉工具

`visionpro_vision_tools` 位于 `source/tools/vision/`，在启用 `VISIONPRO_WITH_OPENCV` 时构建，并私有链接 OpenCV。
工具元数据与适配检查使用 core 的类型，OpenCV 的头文件和 `cv::Mat` 留在视觉实现与工具测试内部。
app 把模拟和视觉工具提供的 `ToolRegistration` 组合成一个 `ToolRegistry`。四个视觉 Schema 已可独立校验，
各工具在具备真实实例工厂后进入运行目录。构建和部署见 [development.md §3.17](development.md#317-s41-release-构建与验证)。

### 2.12 S4.2 图像桥接与文件读取

`visionpro_vision_tools` 私有依赖 `visionpro_infrastructure` 的 `FileResourceLease`。`read_file` 在工作线程通过固定字节解码，
把只读 Image 输出提交给现有执行器。图像桥接集中转换像素布局，并复用 `ImageHandle` 发布独立输出和保留空间元数据。
app 的图像摘要读取类型化 `ImageFrame`。构建和测试见 [development.md §3.18](development.md#318-s42-release-构建与验证)。

### 2.13 S4.3 ROI、继承与掩膜求值

视觉模块的 `evaluate_roi` 使用 `InvocationContextData::regions` 的冻结定义和本次 `mask` 租约，在当前目标图像生成成员掩膜。
几何、采样和方向变换由工具模块负责。执行器的 `RunBindingTrace::regions` 记录已解析的定义、来源路径及调用身份。
`RoiEvaluation` 持有实际成员、分层方向和掩膜来源。S4.4 的 `visionpro.image.threshold` 使用同一求值结果与 OpenCV 桥接，
一次发布独立二值图、展开的 `Region2D` 和成员掩膜。CLI 摘要读取这些类型化输出与冻结生产者身份。

### 2.14 S4.5 连通域与整数范围判断

Blob 通过 OpenCV 桥接复制输入，有 ROI 时应用实际成员掩膜，再将连通域统计发布为类型化结果。普通绑定可按列表索引和 Record 字段读取结果。
整数范围工具的工厂校验固定上下界，执行器按现有工具契约接受技术完成状态、OK/NG 判定和 Bool 输出。NG 的常规后继按控制边继续调度。

S6.3 将整数范围判断与计算、累加、逻辑和格式化工具装入 `visionpro_logic_tools`，桌面与 CLI 共用同一注册表。该库只依赖核心工具契约，无 Qt、无 OpenCV 构建也可运行相同方案。绑定解析、调用状态和条件出口调度仍由 workflow 提供。

### 2.15 S4.6 真实流程与命令行往返

启用 OpenCV 时，CLI 在同一注册表装配四个视觉工具和模拟工具。文件方案通过 `open_solution_execution` 创建快照和执行器，独立调用通过 `RunRequest` 注入只读 Image。
视觉结果使用现有运行结果、来源追溯和控制记录。保存提交配置修订，独立进程重载后通过同一入口重新计算结果。

## 3. 依赖方向

- core 不依赖其他业务模块。
- workflow 和 tools 依赖 core。
- workflow 通过工具接口调用具体实现。
- infrastructure 可以依赖 core 和流程配置模型。
- ui 使用应用命令修改配置和请求运行。
- app 装配具体实现。

初期通过静态工具注册表提供类型描述和运行实例工厂。
app 注册具体能力，WorkflowEngine 通过注册接口创建和调用工具，
不在引擎中按具体算法类型编写分支，也不加载动态插件。
数据绑定解析先于或伴随执行器实现，不能在调用接口固定后再补取值语义。
第三阶段即验证分叉、汇合及基本条件分支，单线程就绪调度即可承担该阶段范围。

core 和 workflow 不依赖 GUI、具体流程编辑器或设备 SDK。
核心领域类型优先使用标准 C++ 类型。
OpenCV 的图像表示可通过受控封装使用，不追求无实际收益的完全隔离。
无 GUI 不等于禁止所有非界面的 Qt 组件；核心执行不能要求窗口、控件
或 GUI 事件处理才能完成。非界面依赖按模块职责评估。

### 3.1 应用调用边界与后端适配

GUI、无 GUI 入口及后续外部调用共用应用服务：
加载/保存/关闭方案，枚举流程/端口，提交 RunRequest，等待/取消 RunHandle，查询结果及订阅事件。
接口不暴露 QWidget、QAxWidget、厂商指针或厂商异常；
应用服务以 core/workflow 契约为基础，由 app 装配具体存储、执行和设备后端。

SDK 的 Solution/Procedure/Group/Tool 分层支持细化调用边界，
但本项目不照搬其进程单例、显示名索引或 void* 对象访问。
若以后接入该 SDK，适配层负责稳定身份映射、UTF-8/原生路径转换、像素/角度转换、
状态码归类、结果物化及调用能力检查；第三方头文件不进入核心公共接口。
后端明确支持的同步/异步、线程安全、并发、一次性输入、结果寿命与关闭协议，
不能从“存在 Run 方法”推断可重入，也不从示例枚举值推断所有工具能力。

这些服务先以本项目原生执行器和模拟后端验证，不因参考 SDK 而引入 COM/ActiveX、
厂商运行时或旧版 Qt 依赖；具体集成属于后续独立适配工作。

## 4. 配置模型与编辑器

VisionPro 的领域模型是流程配置的事实来源。

编辑器通过适配层：

- 读取节点、控制出口、输入输出定义与连接。
- 发起节点增删、控制连接、输入绑定和参数修改命令。
- 将模型变化映射到画布。
- 保存节点位置等布局信息。

不长期维护两套各自可独立修改的流程配置。

S5 已选定 Qt Widgets 与 QtNodes 通用图层，具体适配边界见 §4.1。
画布主连线用于执行编排，普通节点允许多个前驱和后继；
输入源与结果订阅通过独立配置界面表达，QtNodes 适配必须保持该图模型。
可按需显示只读的数据依赖辅助视图，但不改变主连线语义。
工具元数据驱动输入源选择、参数编辑和可订阅结果列表。
编辑动作、结果变化及参数预览不直接触发算法执行或数据消费。

常规编辑器复用参数的类型、范围、单位及绑定能力；复杂 ROI、模板训练使用专用组件。
显示分组、可见性和叠加样式属于 UI 元数据，不参与算法取值或调度。
训练模板、连接设备和刷新设备列表是显式应用命令，不能伪装成参数赋值的隐含副作用。
命令产生的模板等资源通过配置修改纳入后续快照，不改变正在运行的资源版本。
单节点/Group 调试通过显式独立调用提交完整输入，使用独立结果身份和声明的状态策略；
参数预览不能伪装成调试执行，控件刷新也不能代替运行完成信号。

### 4.1 S5 界面与编辑适配

桌面界面使用现有 Qt 6.11.1 `msvc2022_64` 的 Qt Widgets，流程画布采用 QtNodes 3.0.16 通用图层。
QtNodes 负责图形呈现、选择、移动和连接交互；VisionPro 的领域模型仍是配置事实来源。
控件与画布统一发出编辑命令，由应用层校验和修改模型，再刷新界面；不得分别维护可独立修改的配置副本。
QtNodes 的内部身份、数据流行为或序列化格式不替代领域身份、调度与方案文件。
GUI 和无 GUI 入口共用工具装配、应用服务及领域校验，Qt/QtNodes 依赖限定在界面和装配目标。

S5.1 的 `ControlGraphModel` 持有可编辑的 `Solution` 草稿，`ControlScene` 将拖线、删线和节点拖动提交到同一 `QUndoStack`。
Group 导航按 `Containment` 切换当前显示范围，同一场景的命令可在其他层级撤销或重做。
S5.3 的属性检查器按工具元数据编辑参数、输入、资源槽和公开边界，与工作流列表和画布统一提交草稿命令。
后台校验使用草稿副本，界面按稳定身份定位诊断。诊断对应的草稿修改后，关联修复操作等待最新校验结果。
`visionpro_gui` 打开内置画布示例，并和 CLI 通过 `visionpro_app_tools` 共用静态工具装配。启用 OpenCV 时，两种入口都注册真实视觉工具。
S5.5 运行控件通过 `RunController` 在后台准备选中目标的快照和资源，用同会话发布原子受理。文件草稿使用 `publish_solution_run`。
单节点调试以隔离状态策略提交类型化的一次性输入，持久配置由编辑命令管理。运行期间编辑继续进入草稿。
换方案和关闭在后台排空旧会话，下一次受理等待实际清理。控制器按窗口跟踪一轮活动运行。

控制线、输入/参数绑定及 Group 包含关系分别编辑；数据依赖辅助显示只读，不把绑定转为控制边。
基础 Group 编辑包括层级、公开输入输出、入口和导出映射，跨边界操作沿用领域校验并定位诊断。
纯画布分组只影响显示。S6.2 中的普通 Group 按公开接口进入一次子作用域，在组内控制图完成后提交本次数据和选中的控制出口。
S5 单节点调试使用现有独立调用边界，不以自动补跑来源替代缺失输入。

S5.4 的 `ImageView` 将有效像素行复制到 Qt 持有的缓冲，保留只读图像句柄供本地像素和裁剪根坐标查询。
`ImagePanel` 按运行身份校验已有结果的图像、有效 ROI、成员掩膜及 Blob 输出，使用图像局部坐标叠加。
ROI 对话框使用已声明的坐标和工具能力，将全图、矩形、旋转矩形、圆、环、扇环、多边形、继承、修正、排除区和栅格掩膜作为类型化配置提交到同一撤销历史。平面标定、点转换和距离测量与图像工具共用视觉工具注册表，标定节点通过基础设施提供的文件租约读取固定修订。
显式预览在后台读取所选图像并复用 S4 ROI 求值器。同作用域、共用已配置文件图像来源的阈值几何可从草稿解析，其余运行态来源由本轮结果提供。
耗时校验、文件 I/O、资源准备、等待和会话关闭通过后台任务完成，GUI 线程只处理交互与显示。

属性行可直接填写数值和单行文本，按 Enter 或移开焦点提交。布尔值和枚举项选中即提交。每次提交均可单步撤销。“绑定来源…”用于选择上游输出等来源，ROI 和多来源绑定沿用各自的专用编辑器。属性与画布共用草稿和撤销栈，历史中的常量和动态阈值取自所选轮次实际交付给工具的值。

键盘操作时，在工具箱聚焦工具并按 Enter 添加节点。按 `Ctrl+L` 打开“流程 → 连接执行步骤…”，选择当前作用域的起点、执行出口和终点。确认后的控制线可撤销、重做。打开底栏“诊断”，用方向键选择条目，按 Enter 或双击可定位节点。诊断包含已声明的输入或参数时，同时打开属性并将焦点移至对应字段。

`Shift+F5` 取消主工作台所示流程和轮次，停止菜单显示这两个标识。查看已结束的历史轮次时，此命令禁用。打开或关闭运行详情、切换详情内的选择，均保留主工作台的取消对象。要取消详情所选轮次，使用该窗口的“取消此轮”。停止触发源并等待或取消在途运行，仍使用停止菜单中对应的触发源命令。

首次进入流程或 Group 时，画布以 100% 显示并将入口带入视口。右下角小地图显示本层节点、执行连线和当前视口，点击可定位，拖动可平移。下方可放大、缩小、恢复 1:1 或查看全图。切换流程或 Group 后返回时恢复倍率和位置，打开另一方案时清空视图记忆。节点标题以半粗体绘制，长名称可换行。网格随倍率调整疏密，高亮描边标识选中节点，控制线上的箭头标明方向。历史表的判定列用文字和颜色区分 OK 与 NG，执行错误在执行列显示“失败”。

**流程线与分支。** 参考手册印刷第 111–112 页，图 5-107 展示条件检测的 OK/NG，图 5-108 展示分支模块如何用输入值选择后续模块。五路样例中，定位模块的五条线都使用同一个 `matched` 条件，匹配后五路测量全部执行。五个区间判断各自输出检测结果；汇总后的条件节点再选择 OK 或 NG 后继。普通顺序线表示模块正常完成后继续，单路检测得到 NG 也能将结果送到汇总。[VisionMaster V3.0.2 用户手册](Manual/VisionMaster算法平台用户手册V3.0.2.pdf) · [五路检测方案](../samples/s6-inspection/solution.json)

画布平时仅标注已连接的具名条件。同一条件连接多个后继时，条件名称在源节点处标一次。悬停或连线时可查看该模块支持的其他出口，并按需要接入新后继。

#### 图像、历史与统计如何联动

1. **选择节点。** 默认跟随本流程最近受理的整流程轮次。画布选中节点后，右下列出同一方案会话、流程及节点 ID 下的历史，右上和底栏读取当前查看的轮次。当前轮尚未执行该节点、已跳过或未产生有效图时，显示对应原因并清除上一张运行图。多选时保留流程统计，并提示“选一个模块查看结果”。
2. **选择图像。** 图像输出直接显示。Blob 与颜色测量叠加本次调用的包围框、质心或有效 ROI。第五路判断自动显示其唯一测量来源的图像及模块名。若有多个可显示的上游来源，从下拉框选择，切换轮次时继续查看能唯一匹配的来源。同一图源的尺寸、坐标系和裁剪原点一致时保留缩放和位置，来源或几何变化时重新适应窗口。输出图获得焦点后，用 `+`、`-` 缩放，按 `1` 切到原始像素倍率，方向键逐像素查看当前轮次的读数。
3. **查看历史。** 点击某一行即固定该轮和调用。右上显示该调用的图像，底栏切到同轮统计并标出“历史”。新轮到达只向表中增加记录。同流程内点另一个节点，继续查看固定轮次，可在该轮的多次调用间切换；该轮无结果时显示原因。点击“跟随最新”回到实时查看。Group、循环与重入通过会话、快照、轮次、节点、作用域及调用身份区分。一次调用的重试在详情展开，早期尝试仅显示已有的状态和诊断。单节点隔离调试和独立 Group 运行在详情中按来源区分。
4. **变更上下文。** 切流程时按目标流程重新选择轮次和模块；换方案时释放旧选择、图像和固定句柄。编辑参数后，已有结果保留原轮次、快照与阈值；下一轮运行受理后转入新快照。图像、结果摘要和统计一起切换；迟到的刷新回调须核对选择身份。

**统计口径。** “已派发”取 `RunProgress::call_order.size()`，循环体的每次派发分别计数。执行器用单调时钟记录从开始执行到首次逻辑终态的流程耗时。模块耗时取该调用最终结果中的 `elapsed`，算法耗时取带已知单位的 `ToolAlgorithm` 测量，缺测显示“—”。流程状态取执行器的技术状态。“区间判断”统计本轮已发布 OK/NG 的整数、浮点范围判断调用，五路案例中恰好对应五个判断节点。[运行进度](../include/visionpro/workflow/run_handle.hpp) · [计时类型](../include/visionpro/core/timing.hpp)

**观察与刷新。** 工作区订阅运行变化，右下历史和画布底栏共用所选轮次与调用。已结束轮次复用摘要，右上仅在所选结果身份或输出改变时重新取图。关闭“运行详情”后，六区仍正常更新。

## 5. 配置与执行

编辑模型经方案级不变量检查可捕获不可变 ConfigSnapshot。所选范围的领域和能力检查通过后形成执行计划。
加载校验与执行校验分开：缺工具/资源的模型可带诊断编辑，不能误执行。
执行计划由快照和执行器能力共同决定；计划生成失败不删除模型中的合法目标结构。

`ExecutionPlan::create` 在不可变配置快照上复用绑定校验，生成只读执行计划。
计划包含控制图及入边状态规则、由绑定派生的依赖约束、来源作用域及所需资源能力，
并关联配置快照身份、工具定义版本和执行器支持范围。
运行只持有一份计划；编辑后重新校验生成新计划，仅供后续运行使用。
计划是可重新生成的运行产物，不作为方案文件中的另一份可编辑流程。

规划检查稳定标识、绑定/选择器/转换、控制激活、作用域及不支持能力。
控制关系决定执行许可，数据就绪约束可细化未规定的顺序；
例如同一分叉下已激活的兄弟节点可以按依赖先后执行。
不能反转明确控制顺序、激活未选分支或补跑副作用来源；Optional 不放宽该规则。
控制、数据与已声明资源等待约束共同校验，不能只检查数据图无环。
资源能力在规划时校验；连接、占用及设备断开等动态状态在运行时另行处理。

职责按以下路径分开：

```text
ToolDescriptor：工具类型及输入输出、参数元数据
Node：方案中的模块配置与绑定
Node 配置快照 → 工厂创建 ToolInstance → 执行产生 NodeResult
```

Node 是配置，不兼任执行对象；ToolInstance 是运行实例，不负责编辑或保存方案。
实例只能使用当前快照和本次已解析输入，不能借用可变编辑配置绕过快照边界。
实例创建失败应报告节点诊断，不删除或改写配置。
停止或释放运行实例不删除节点配置，编辑节点也不直接重置正在使用的实例。
跨调用状态由 NodeState 的作用域和重置策略管理，不保存到 Node 或结果历史中。
工具元数据声明状态能力与约束，节点配置选择工具允许的初值、每轮初始化或跨轮累计行为。
快照/计划准备复用已校验的类型化节点参数，生成各节点不可变的有效状态规格；
状态服务据此管理 Init、重置、访问与代次，不把某节点的选择写回共享工具描述。
S3.1 通过 `ToolDescriptor.state_parameters` 声明投影，将节点选择固定在 `ToolExecutionConfiguration::effective_state()`。
S3.5 使用该规格分配状态和访问权，具体契约见 data-model §2.1、§13。
实例寿命可按调用、运行或会话声明，状态寿命独立选择 Invocation、WorkflowRun、SolutionSession。
首批执行器按调用创建实例，通过引擎的节点状态仓库保留会话状态并协调首次 Init。
工具声明配置兼容性，不兼容配置创建新状态代次，在途快照继续使用原代次。
同类型节点互不共享可变状态，改名和布局变化不重置状态。

WorkflowEngine 是运行服务，Workflow 是可持久化模型，二者不互相兼任。
S3.2–S3.5 已接通运行准入、结果提交、异步生命周期、分路调度、工具状态与单节点调用。
详细配置与运行边界见 [data-model.md](data-model.md)。

运行上下文保存：

- 本次运行标识。
- 节点输出与诊断。
- 取消状态。
- 执行统计。
- 本轮工具状态及对受控会话服务的访问入口。

运行上下文不回写节点配置。
外部图像、标量或 ROI 经 RunRequest 与快照一起受理；Busy 不修改待运行输入。
工作流公开端口映射到内部绑定，每轮输入独立且默认不持久化，详见 data-model §4.1。
运行期间的编辑何时生效由应用策略决定，
不得使同一轮执行混用不同版本的参数。

独立单节点调用由应用服务固定目标及本次输入，运行准备直接校验目标输入 Schema，
不借原流程入口或上游绑定补齐输入，也不激活目标外的后继；参数、资源及状态仍遵守工具契约。
S3.1 的 NodeTarget 计划把 RunRequest 的固定值直接交给 PreparedTool，定位无法取得的上游参数订阅。
S3.5 验证了独立执行准入与调试状态隔离，输入与缺值规则见 data-model §5.5。

一次节点调用按以下顺序处理：

1. 调度器按控制到达/关闭状态确定执行许可，并按数据就绪条件排入可执行队列。
2. 启动前检查取消，在本次运行/作用域中解析输入与可订阅参数；Pending 不能提前变为 None。
3. 校验类型、选择器、转换、范围与坐标，固定本次调用输入。
4. 获取资源租约并创建工具实例。状态工具先按域 Init 并附加状态访问权，再启动 InvocationOperation，同步执行或等待异步完成通知。
5. 校验输出契约、身份及尝试提交资格，一次性接受结果和终态，并一致地产生控制完成事件。
6. 引擎根据已接受状态及已验证出口选择推进/关闭后继；真正启动后继前再次检查取消。
7. 实际操作退出后归还租约并释放不再需要的对象，不以逻辑终态替代物理退出。

InvocationOperation 持有快照、固定输入、状态/资源访问和取消入口。
S3.3 的执行器通过 `notify_when` 接收逻辑完成和实际退出唤醒，按当前调用身份处理。
异步工具不得在回调仍可能使用数据时释放这些对象；同步返回不得遗留未追踪的后台业务操作。
工具只报告结果及允许的出口选择，不直接调度后继。预期错误返回诊断，异常在调用边界截获。
初始化准备状态和资源，业务采集、消费、发送仍是显式调用。

绑定不自动调度源节点。合法路径上的来源尚未完成时可等待其就绪，
确定不可能产生必需值时报告缺失/依赖错误，不能自动读取上一轮值或改变明确编排顺序。
例如控制顺序为 B → A，而 B 必须读取 A 的本轮输出，应报告依赖冲突，
不能自动补跑 A；A 可能执行采集、队列消费或通信操作。
外部读写、全局写入和队列消费由显式操作负责；输出发布不表示这些操作可整体回滚。

第三阶段可采用单工作线程就绪队列和每流程 maxInFlight=1；重复启动返回 Busy，
不隐式排队、替换或取消旧运行，槽位保留至实际调用和清理完成。
该策略不限制图的分叉/汇合，也不是方案会话全局互斥。
节点默认使用 FailFast，自动重试次数为 0。S6.7 允许工具节点通过错误出口显式继续，重试资格由注册的工具能力和当前诊断共同决定。
已处理失败不改写原节点状态；重试中间失败不提前触发最终错误出口。
连续/外部触发、重入和并行的准入与取消范围分别声明，资源冲突只约束相关操作。
超时或取消使结果失去提交资格，不表示工作线程、设备操作或资源租约已经结束；
实例与资源仍需保留至实际操作退出，清理未完成前不能对同一实例或独占资源启动冲突操作。
支持异步等待后采用事件通知或条件等待，不能通过持续空转检查就绪状态。

S6.5 由 `WorkflowEngine` 分别管理每个流程的在途槽位与 FIFO 等待队列。执行线程池按实际受理的槽位扩展，同一轮在任一时刻只由一个线程推进。执行器在调度锁之外运行节点、等待资源并释放本轮工作对象。调用仲裁器在绑定就绪后一次申请涉及的资源 ID 和串行状态代次，允许无关调用独立推进。工具工厂及资源提供方可以接收不同轮次的并发调用。桌面按运行身份保留在途句柄并提交取消。[准入与状态契约](data-model.md#54-多流程触发与并发c06)

S6.7 在执行器中按逻辑调用仲裁取消、单次尝试的期限和结果提交。运行包含定时工具时，工具启动和协作取消可在单独线程执行，同轮其他节点仍能处理到期事件。执行器按稳态时钟记录完成时刻，先登记尝试的状态，再等待实际退出并归还租约。重试重新申请资源，使用原输入和配置创建新实例。最终失败仅能激活已连接且目标启用的错误出口。[调用与恢复契约](data-model.md#83-结果提交取消与副作用)

无 GUI 验证先采用内存配置和模拟工具，随后接入配置存储和真实算法。
每次调用记录配置快照身份、运行与调用标识、实际来源、顺序及诊断，
支持追溯但不默认保存全部图像缓冲区，也不声称外部副作用可精确重放。

### 5.1 单次、连续与停止

单次运行的同步等待与异步受理复用同一调用契约，RunHandle 明确受理、完成和实际退出。
S6.6 由 `TriggerControl` 将事件转换为单次 `RunRequest`。桌面在工作线程提交，CLI 可逐次推进受控时钟。订阅绑定活动方案会话及流程入口，每个事件读取当时已发布的快照，再按流程准入策略提交。启用桌面触发可单独发布草稿，保留同一会话的兼容状态。时钟超过一个或多个间隔时，本次推进只生成一帧，下一次最早触发时刻从本次推进计算。[触发控制接口](../include/visionpro/workflow/trigger_control.hpp)

停止订阅与最终准入使用同一把锁。资源预检在锁外进行，预检结束后重新检查配置快照与订阅状态。`disarm()` 封住入口，`stop(Drain)` 等待本订阅已受理的工作实际退出，`stop(Cancel)` 先请求取消再等待。等待期限覆盖预检返回和运行实际退出，超时后可用同一订阅继续等待。桌面换方案时先撤销事件入口，再由后台关闭会话并等待预检退出。[停止与租约验收](development.md#106-s66-连续运行与外部触发)
方案级命令固定参与的启用流程集合，保留每个 WorkflowRunId 及整体摘要，
不能只返回一个 bool 隐藏某个流程未受理/失败；并行与聚合在第六阶段实现。

### 5.2 会话切换与退出

app 显式协调启动与 shutdown；加载/保存/导入/关闭有独立管理操作身份与结果，
不把进度事件或“结束”回调直接视为成功。
加载候选模型成功后再切换活动会话；后端单例限制或加载期间接口不可调用时，
由该后端管理命令串行化/停稳处理，模型加载失败保护仍须成立。

S3.6 已验证内存候选校验失败时保留活动会话。切换和关闭进入管理状态后停止受理，
旧引擎保留必要完成通道至所有在途操作实际退出，再释放会话持有的索引、状态及资源引用。
新会话使用独立身份和观察通道。文件加载和真实后端的管理调用按后续阶段接入。

退出顺序为：停止新请求和触发 → 关闭可选观察交付、请求排空/取消
→ 保持必要完成/退出通知直到活动操作实际退出 → 撤销底层回调并等已进入回调退出
→ 释放结果/状态及资源访问 → 关闭连接/后端 → 最终进程资源清理。
具体后端若要求不同依赖顺序，须声明并验证，但不能提前销毁回调用户对象或图像缓冲。
厂商要求显式调用的 DisposeResource 与控件 dispose 位于对应生命周期中，
不因此否定普通资源的 RAII，也不把窗口析构作为整个核心系统的退出入口。

### 5.3 S5.2 同会话配置发布

`WorkflowSession::publish_and_submit` 从活动捕获、当前草稿和本次运行参数准备新运行。
准备阶段在会话锁外检查方案级不变量、所选执行范围、工具能力及资源。受理时复查运行槽位，并在会话锁内同时提交本次运行和更新活动快照及资源提供方。
业务校验失败返回诊断，槽位被占用返回忙。两种结果均保留活动配置。

`Publish`、`Activate` 和 `Close` 使用同一管理操作保留机制。准备发布时活动配置仍可查询，普通提交在受理前复查捕获是否仍为活动配置。
方案替换和关闭沿用 §5.2 的排空协议。发布保留引擎、观察通道和会话身份，工具状态按既有兼容规则延续或建立新代次。

受理工作项持有与预检相同的资源提供方，直到本轮后继和实际退出后的清理均完成。已保留的结果历史继续使用运行身份和调用记录。
文件方案通过 `publish_solution_run` 从草稿和文档路径上下文创建提供方。运行触发时的草稿捕获、文件资源准备与关闭等待由调用方安排在后台。
读取策略和 API 契约见 [data-model §4.15](data-model.md#415-s52-同会话配置发布)。

## 6. 三类关系

- 控制关系：描述执行顺序及控制转移。
- 数据关系：描述输入从何处获取数据。
- 包含关系：描述节点属于哪个流程或结构化容器。

三类关系不能互相替代。
控制连线不隐含数据绑定，数据绑定不直接触发执行。
数据依赖仍约束控制关系的合法性，必须检查来源在当前路径中能否产生有效输出。

循环不能仅靠允许任意回边获得语义。
跨流程传递不能仅靠放开普通数据引用获得同步保证。
分支可能激活一个或多个出口，多出口不自动意味着并行执行。
循环需要独立执行作用域；汇合需要定义哪些分路应到达以及如何处理未执行分路。

C06 的详细语义以 data-model §5.2–§5.4 为准，架构责任如下：

- 控制图支持普通节点多前驱/多后继，无条件分叉激活全部后继，条件出口允许零个、一个或多个。
- 引擎按运行/作用域维护每条入边的 Pending、Arrived、Closed(reason)，处理重复通知和嵌套关闭传播。
- 触发向显式入口注入一次启动许可；规划诊断范围外前驱连入执行节点的情况，不能保留无完成来源的等待。
- AllActivated 等全部入边已确定及参与路径完成后，至少有一条有效到达才执行节点一次。
- 全部正常未选时不执行并传播关闭；失败/取消不能冒充 NotSelected，按 C08 处理并解除等待。
- 汇合策略附着节点控制配置和计划，不强制画布插入虚拟业务节点。
- MergeValues 是显式数据聚合，控制到达不自动决定缺失字段取值。
- 循环区域进入时解析边界和捕获输入。`ScopedSchedule` 为每次迭代分配子作用域和独立控制状态。调度器按截止时间唤醒下一次迭代，间隔内可响应取消及其他已就绪工作。
- `LoopExecution` 按迭代顺序维护 First、Last、Collect 和带初值的数值 Sum。区域成功后向结果仓库提交一次公开输出，取消及失败保留逐次诊断和调用记录。
- 跨流程 CorrelationJoiner 是业务数据服务，不复用流程内控制到达语义。

S3.4 已实现根作用域分叉、AllActivated 和基本分支。S6.1 将控制调度复用到嵌套循环作用域。执行计划能力通过 `structured_loops` 显式声明。[循环与导出契约](data-model.md#53-结构化循环与作用域c06)
AnySelected 等提前继续策略在剩余工作取消/收尾规则明确后再开放。
复合 Group 封装子图和公开输入输出，纯画布分组不产生运行作用域；
查询接口分别提供当前层和递归层级，独立 Group 必须显式注入宿主资源和状态服务。
S6.2 的桌面与 CLI 复用同一 Group 执行计划及结果仓库。独立调用使用 NodeTarget 和显式宿主，导入服务重映射实例及内部工具身份。[Group 边界规则](data-model.md#55-复合子图独立调用与启用策略c01c04c06)

下图对应手册图 3-2 的编排需求；线条仅表示控制，数据经独立绑定获取：

```mermaid

    Input[本地图像] --> Color[颜色转换] --> Match[特征定位]
```

## 7. 运行数据服务

| 服务 | 职责与作用域 |
|---|---|
| BindingResolver | 解析类型化引用，不拥有共享业务值，也不消费队列 |
| ResultStore | 保存按运行、作用域和调用区分的节点结果 |
| SharedDataService | 管理方案会话内的全局值、版本与写入来源，提供原子批量读写、有界 FIFO 和多队列组合接收 |
| CorrelationJoinService | 按命名汇合、批次和工件关联键暂存来源字段，输出齐备的记录及重复、过期、容量等统计 |
| NodeStateStore | 管理按节点与状态作用域隔离的累积或初始化状态 |
| 事件交付适配 | 分离内部完成、业务结果和显示通知，管理订阅/注销、队列容量与来源身份 |

这些服务属于 workflow 的逻辑职责，不要求各自建立独立库或通用框架。
结果历史显示可以维护索引，但不能将“节点最新结果”作为运行时引用解析依据。
需要保持的图像结果必须具有有效所有权，历史缓存应按条数、字节或时间设置保留上限。
活动调用、队列和共享值仍持有的缓冲区不能被历史淘汰强制释放。
容量不足时明确拒绝、等待或按已声明策略丢弃，不能通过丢弃必需业务数据伪装成功。

全局变量支持显式读写工具及元数据允许的只读 GlobalReference；
后者记录版本与取值时机，批量一致读取由共享服务提供，写入仍是显式副作用。
多个全局值的一致快照不代表它们属于同一工件，仍需关联标识或明确同步。
队列传递完整记录；多生产者的字段先按关联标识汇合，再原子入队。
需要组合消费多队列时，必须定义齐备与消费原子性，避免只取走部分数据。
S6.4 中，`WorkflowSession` 通过执行器持有这两项服务。已声明共享能力的工具按本轮配置取得服务视图。队列操作可异步等待，取消或会话关闭可唤醒等待者，执行线程可继续推进其他就绪节点。隔离调试使用私有服务。桌面通过会话取得只读预览，CLI 在新会话使用同一注册表和执行路径。[服务契约](data-model.md#12-数据队列)

脚本复用普通工具的输入输出契约，以受控接口访问共享服务，
不直接访问 GUI、全局容器或其他节点的可变内存。

SDK 回调可来自后台线程且影响下一轮启动。适配器只完成必要校验、数据物化/持有与入队，
引擎校验身份后提交，UI 再于 GUI 线程显示，不能在回调中同步渲染或等待本运行。
可选结果通知与必要结果物化分别控制；禁止因关闭显示回调而断开数据依赖或控制推进。
注销返回不自动证明回调已退出，订阅对象须在后端确认无回调访问后释放；
如果关联身份不充分，只收窄该后端对象的在途范围，不能将限制传播为全方案单链。
脚本语言与执行后端不在当前阶段选定。

## 8. 图像与结果

- 图像缓冲区拥有者与读取者必须明确。
- 节点输出发布后按只读共享处理。
- 原地修改需要独立所有权或显式复制。
- 几何结果与显示叠加层分开。
- ROI 保留浮点几何、局部方向、继承/排除与修正，不默认取整数包围框。
- 工具声明格式、几何/掩膜及组合能力；坐标、单位和变换在适配层显式转换。
- 外部图像校验格式、步长、尺寸和缓冲长度，结构浅拷贝不延长借用数据寿命。
- 结果适配逐输出检查状态与数量；源节点成功不自动意味着每个输出都可用。
- core 的输出元数据声明必需性与合法不产出原因，tools/适配层报告每个输出的可用性，workflow 校验后接受结果。
- 合法 NotProduced、值级 None/空集合与 Invalid 分开处理；Invalid 默认使整次调用失败，数据未产生不自动改变控制编排。
- 结果带运行来源，避免显示或消费过期数据。

固定资源版本、动态采集图像和显示历史分别管理；
图像裁剪视图持有父缓冲，历史淘汰只释放自身引用。
S3.1 在工具完成、结果物化及绑定解析间保留已声明的不产出原因与失效诊断，见 data-model §8.1.1。

core 定义类型化的外部诊断与耗时表示，infrastructure 适配层按已知接口语义映射原码、测量范围和单位，
workflow 保留这些证据与本次调用关联，ui/日志不从数值零或显示文本猜测成功、NG 或耗时是否已测得。
S3.1 用模拟完成载荷验证外部诊断和多范围耗时的投影。S3.6 通过内存模拟适配验证不同状态域的成功码和外部缓冲物化，见 data-model §9。

### 8.1 S5 结果呈现与观察

S5.5 默认保留 16 轮已清理运行，观察队列容量默认 32，两者可由运行菜单配置。窗口持有有界的运行句柄，面板可固定正在查看的旧轮。

## 9. 资源与持久化

方案配置引用资源，资源解析由独立服务负责。

设备连接与节点执行实例分离：infrastructure 中的相机、通信适配器拥有连接和 SDK 句柄；
core 声明工具所需的最小资源能力接口，app 在无 GUI 和 GUI 入口注入相同服务。
ToolInstance 通过 ResourceId 获取受控访问或租约，只执行采集、发送等具体操作。
节点释放不默认断开其他节点正在使用的连接，资源服务负责最终关闭与清理。
共享连接不代表设备可重入；独占、串行访问、超时和断连恢复在接入该资源前确定。
S6.10 的 `CameraLease` 按适配器和序列号独占物理设备，资源别名也共用该限制。采集节点在工作线程取得一帧并关闭；流程触发入口在布防期间持有租约，每取得一帧就把该帧的图像和帧号交给同一轮运行。停止入口先关闭新轮准入，再取消等待，等待读取与设备关闭后归还租约。重连需重新布防，取得新的订阅身份。MVS 适配器在归还 SDK 缓冲前复制像素，SDK 类型只在 infrastructure 内部使用。[相机接口](../include/visionpro/infrastructure/camera.hpp) · [触发流](../source/infrastructure/camera_trigger.cpp)

S6.11 在资源提供方内按资源 ID 保存 `CommunicationLease`。加载和预检只校验端点配置，首次显式 I/O 在工作线程连接，后续节点可以沿同一连接继续读取。租约将单次操作串行化，等待访问、连接、收发共用一个单调时钟截止时间。断流或响应损坏时关闭该连接并丢弃残帧，下次显式操作重新建立连接。Modbus 读写在同一次操作内核对事务及响应。通用 TCP 的发送和接收是分开的节点，需要由调用方案安排顺序或在载荷中携带工件键。资源提供方和运行释放引用后关闭套接字。[端点接口](../include/visionpro/infrastructure/communication.hpp) · [套接字与协议实现](../source/infrastructure/communication.cpp)

资源目录区分托管版本、外部文件、目录/图像序列、设备逻辑引用和输出路径/命名。
固定模板/标定版本随计划锁定；动态输入在采集时读取并追溯实际来源。
用户可选择保留引用或嵌入，便携导出须报告残留外部依赖。
相对路径有显式基准，不能依赖进程工作目录；保存不改写外部文件。

方案格式不直接等同于内存对象布局。
方案版本、工具配置版本和资源引用规则分别定义。
全局变量保存类型与初值，队列保存消息定义和容量策略；
节点状态初值与重置选择随其类型化配置保存，运行时有效状态规格由配置和工具约束重新生成；
当前共享值、积压消息、工具累积状态与运行结果默认不属于方案文件。
后续如需恢复运行状态，应单独设计检查点机制，不改变普通配置保存的含义。

首个后端采用目录加 JSON 清单，托管资源先写不可变新版本，清单以同文件系统临时文件原子提交。
提交前失败不破坏旧方案，提交后清理失败单独报告；修订比较与提交由同一后端协议保护，
无法协调的第三方写入按实际能力报告，不把单次预检查当作原子防冲突。
S3.7 将文件解析、领域诊断与执行预检分层。缺资源或工具的已知格式可打开查看和修复。
新清单在同卷完成写入后发布，已有清单受保护。未知字段的文档保留已知视图，保存与执行入口返回兼容性诊断。
S3.8 已接通协作保存者的修订比较、清单替换和可重试的资源清理，具体协议见 [§2.9](#29-s38-保存事务与故障保护)。
单文件、打包或加密作为后续后端能力，不改变领域契约。
流程/Group 复用采用明确端口 Schema 与资源依赖清单，导入新实例须重映射内部身份，
不能按显示名称绑定目标方案同名对象，也不导入运行状态；完整功能在第六阶段实现。
具体保存/加载规则见 data-model §10。

### 9.1 S5.3 文档与资源操作

新建方案先形成带稳定身份的内存草稿，未保存但通过所选范围校验的草稿可以运行。
未确定方案目录时，资源路径必须使用明确绝对路径或命名根，不能借用进程工作目录解释方案相对路径。
首次保存确定方案目录，文件操作继续由 infrastructure 承担，应用层维护编辑稿、保存基线和运行快照的区别。

选择文件默认建立外部引用，复制资源进入方案是显式操作；保存不改写外部源文件。
S5 不新增完整托管导入及其实际 SHA-256 验收，既有摘要与修订能力保持；后续扩大范围时补充对应验收。
不能将 S4 的无摘要验收结论扩展为托管路径已通过本轮验证。

桌面通过后台任务调用 `load_solution`、`save_solution` 和 `transfer_solution`。当前画布在文件操作成功后才接收新文档。
普通保存以已加载清单为基线。成功时更新修订和撤销历史的保存标记，通过精确匹配提交内容刷新基线。清理或基线刷新失败与清单提交结果分别呈现。

`transfer_solution` 先准备被引用的包内文件及新路径，再发布新清单。另存为保留身份和修订，独立复制生成新身份并重映射内部引用。
包外文件保持原目标，界面报告外部文件与待配置命名根。成功转移后编辑器打开目标文档并为该文档开始新的撤销历史。[文件边界](data-model.md#105-s53-新建与资源往返)

- 动态插件 ABI。

## 12. SDK 指南补充的设计取舍

依据为 [SDK 开发指南 V4.3.1（C++）](<Manual/VisionMaster算法平台SDK开发指南V4.3.1（C++）.chm>)，
具体章节/接口与版本差异见 requirements §2.1。以下是本项目决策，不推断厂商内部算法。

| SDK 中可观察的接口/用法 | 本项目采纳或调整 | 契约落点 |
|---|---|---|
| Solution/Procedure/Group/Tool 分层、Run 的等待选项 | 统一应用服务与显式作用域，返回可追溯运行句柄；不采用进程全局单例作为领域模型 | C01、C06、C07 |
| SetInputImage/ROI 每次执行后清空 | 一次性类型化运行输入与快照一起受理；重试复用同一数据并按适配器要求重新注入 | C03、C04 |
| Group 动态端口、独立加载和分层模块枚举 | 复合子图公开 Schema、宿主依赖和层级查询；不允许外部任意穿透内部结果 | C01、C04、C06、C09 |
| GetResult 刷新、nValueStatus 与结果缓存 | 物化本轮不可变结果，逐输出校验；SDK 缓存不代替 ResultStore 的身份和保留契约 | C02、C03、C08 |
| 几何 ROI 与 mask 设置 | 补齐 RasterMask 与转换/组合能力；互斥限制归具体工具，不降低通用区域模型 | C05 |
| 回调线程、启停回调、异步控件刷新 | 内部完成、业务交付、UI 观察分层；注销须确认静默，显示刷新不作为完成依据 | C07、C08、C10 |
| 管理接口非线程安全、StopRun 等待、DisposeResource | 后端命令协调、连续停止与取消分离、显式退出；不照搬析构样例，不引入全方案执行锁 | C01、C06、C07 |
| 多类错误码、版本升级和弃用接口 | 保留原始错误域/码与后端版本，按接口能力映射；迁移/SDK 环境另行验证 | C08、C09、C10 |

SDK 的字符串参数/名称路径可用于外围映射，不代替本项目稳定 ID 与强类型绑定。
Qt5.0–5.10、MSVC、QAxWidget 等是该版厂商控件章节的描述，不是本项目依赖版本决定。
本文未引入 SDK 链接、控件嵌入或方案格式兼容承诺，也未将 SDK 样例视为已运行证据。
